Visual recording · architecture & delivery plan

Store the view.
Not every repaint.

Record many terminals for days. Keep the meaningful visual changes and the events that explain them. Watch live, rewind, and export course footage without stopping capture.

Your goal

An idle screen stays small

One unchanged view can last eight hours. Repainting it 30,000 times should not store 30,000 copies.

Recommended design

Visual states + event timeline

Reusable screen rows, timed state references, and indexed activity in a private SQLite recording.

Your latest decision

Keep recording; show fidelity gaps

If detected visuals cannot be reproduced, continue supported recording and explicitly mark affected intervals incomplete.

The main risk is fidelity and timing—not compression.

We need to prove the terminal engine reproduces supported visuals, and place events correctly even when the screen has been idle for hours. Those are the first gates, not work left until the end.

B. One line changes in a 62-row terminal

Storage example
View A = [row 1, row 2, …, row 60, row 61, row 62]
View B = [row 1, row 2, …, NEW row 60, row 61, row 62]

Store the new row, a small complete list of row references, and a presentation timestamp. Reuse the other 61 rows. Cursor changes use separate presentation metadata.

Why not a long chain of “change this cell” patches?

A long patch chain makes a late seek depend on replaying earlier changes. Each proposed screen state instead contains a complete ordered row-reference list. Loading a state costs a bounded number of row lookups, independent of whether it occurred ten minutes or three days into the recording.

Rows and state definitions are compressed and deduplicated within one recording. The lookup cache is bounded; the full content index lives on disk. No shared dictionary across private recordings is needed.

C. A spinner repeats while the agent works

Baseline + stretch goal

First version

Store A, B, C once.

Timeline:
A → B → C → A → B → C …

The pixels/cells do not keep duplicating. Small timed references still grow with each visible transition.

Optional later optimization

Pattern: A → B → C
Repeat: 900 times
Tail: A → B

Preserve observed timing.

Exact repeats can become a compact loop. Jitter needs timing residuals or ordinary references; we never invent a fixed period.

Reuse first. Loop detection second. No promise of constant storage for genuinely changing content or irregular animation.

D. Export a lesson without ending the recording

Concurrent export
Export range: 10:15–10:27
Visual cutoff: committed sequence 48,210
Event cutoff: event sequence 1,953
Render recipe: 1440p · selected font · cursor steady

Capture meanwhile: sequence 48,211 → 48,212 → …

The export reads a fixed selection of immutable content. Later footage and events do not change that export. Its recipe can change size, framing, padding, cursor policy, cuts, or speed without modifying the recording.

Later-arriving events are not silently inserted into an existing export. Exporting “up to now” stops at a trustworthy committed boundary, not an optimistic live estimate.

03

Decision ledger

The visual-recording epic is approved for development on the merged Go-first UX. Design descriptions below are not claims of implementation or qualification. Baseline evidence and scope ownership distinguish completed raw-history features from remaining visual-format work.

Confirmed
Visual footage is the preservation goal.

Keep what a supported terminal view looks like over time, not every redundant byte emitted to repaint it. Exact original asciicast reconstruction is not a requirement for the new visual format.

Confirmed
Continue through detected fidelity limitations.

Preserve supported text/cursor footage, flag affected intervals incomplete, and continue other captures normally. Unsupported visuals may be permanently absent. No automatic raw fallback has been selected.

Confirmed
Capture, viewing, and export are independent.

Days-long capture, concurrent historical navigation, export without stopping, and tens of terminals are core requirements.

Proposed
SQLite/WAL per recording; zstd-compressed reusable rows.

Use an established transactional store for indexes, concurrent readers, durable ordering, and events. Avoid designing another low-level container and index from scratch.

Proposed
Extend the existing avt helper; retain the official renderer.

Reuse the packaged avt 0.18 helper, completed Go application and four thin browser adapters. Prove canonical visible readout AND a bounded ANSI repaint projection into the unmodified player before freezing the schema. No new GUI, emulator or independent Go pixel renderer.

Proposed
No silent temporal thinning.

Initially preserve distinct source-timed visual states and ordering. Repaint grouping and synchronized-output rules must be explicit and tested; do not quietly drop short-lived states using a guessed debounce window.

Proposed
Keep old archives; switch new writes only after qualification.

Existing raw archives remain readable and untouched. New-format capture becomes the normal writer only after synthetic, reference-renderer, actual-backend, and scale checks. No active archive migration.

Must prove
Timing, source coverage, and scale.

Accurate idle-period event placement, terminal feature support, supported capture geometry, bounded 32-terminal resource use, and non-growing WAL files require evidence.

What “continue best-effort” means in the UI, export, and failure handling
  • Live view: keep displaying supported content. Show a visible “fidelity incomplete” badge with the detected feature and affected interval.
  • Timeline: store sparse fidelity events. Repeated identical warnings can update an open interval rather than flood the activity store.
  • Export: include fidelity intervals in the export manifest and warn before export. Do not call the result fully faithful. Whether to burn a warning into the video is a presentation choice, not an automatic mutation of footage.
  • Recovery: do not clear a warning merely because output continues. An unsupported stateful sequence may affect later interpretation; keep uncertainty until a justified reset/reinitialization or recovery condition.
  • Actual failure: disk-full, corruption, or an unusable parser remains an interruption/failure, not a reason to claim best-effort success. Other recordings stay independent.

A converter can flag detected unsupported input. It cannot detect every visual omitted by an upstream watch stream. Capture qualification and source limitations must remain separately visible.

What stays in memory

One current terminal state per target: visible cells plus hidden parser/mode state required to interpret future output. Bounded queues and caches.

No browser per recording. No history-sized replay buffer. Deduplication reduces storage, but repeated source output still costs parsing CPU.

What stays on disk

Compressed reusable rows, complete row-reference views, timed presentation records, sparse events, segment metadata, and durable progress.

No permanent raw duplicate by default after qualification. No global cross-recording content dictionary. No automatic deletion.

Storage model: an application format on SQLite, not a new binary container

“Our format” means our documented visual schema and interpretation rules. SQLite supplies the underlying file structure and transactions. Zstd compresses content, as it already does today.

Logical recordStored information
Row contentCanonical cell text/graphemes, widths, styling and color references; compressed payload, content hash, decoded size.
Screen definitionDimensions and complete ordered row IDs; relevant palette/theme state and schema identity.
Presentation entrySegment, sequence, start time, screen ID, visible cursor and supported overlay/animation state.
Activity eventEvent identity, producer/agent attribution, kind, bounded metadata, receipt/source times and footage placement uncertainty.
Segment / progressClock mapping, lifecycle boundaries, verified committed endpoint, fidelity intervals and interruption status.

Unchanged states extend a hold rather than append another visual record. The current hold endpoint/progress is a small mutable record; finalized content remains immutable. Hash matches must be checked against canonical content rather than trusted as permission to merge arbitrary payloads.

Use a distinct format identifier and explicit reader dispatch. Do not repurpose the old archive's inert legacy version field. Keep existing raw readers for existing recordings.

Implementation qualification: the current Go package disables cgo. A maintained pure-Go SQLite driver or another packaging-compatible binding must be selected and tested. WAL checkpoints, database/cache limits, dependencies, licenses, and reproducible Nix builds are part of the work.

Timing: how an event at 02:00 lands correctly on an idle screen

Current anchors use the latest validated cast timestamp. That clock does not advance until another source event arrives. It cannot directly place an event received long after the last repaint.

The new capture-clock contract must establish a shared timing relationship, including an idle coverage boundary. Source times, receipt times, and durable publication times are different facts:

source frontier = coverage established by capture
received frontier = input the converter has received
durable frontier = verified data committed to storage
live estimate = labelled extrapolation, not export proof
  • Use defined integer/rational media time and preserve ordering; do not base edits on floating-point accumulation or wall-clock subtraction.
  • Keep producer-declared time separate from recorder receipt time. Record uncertainty when correlation is approximate.
  • Test delayed FIFO delivery, idle tails, backlog and clock changes. If needed, add capture-side timing/barriers instead of guessing.
  • Pause ends a segment. Events during the gap remain events without invented footage. Resume establishes a fresh segment.
  • Export freezes both content and event cutoffs. Late arrivals cannot alter a frozen result.

Gate: precise idle source coverage is not yet established. If unavailable, show trailing holds/event placements as estimated or unknown, retain the verified frontier, and continue useful storage/GUI work. Default exports end at verified durable coverage; an estimated-tail export requires separate approval. Heartbeats and live process checks never prove “all source footage observed through now.”

Event coverage, privacy, selections, and panel actions

Reuse the existing event ingress and actor attribution. Replace its fixed lifetime record cap with indexed history plus bounded per-request and pending-queue limits.

ExampleWhere the evidence comes from
Agent turn endedAgent integration hook. Actor and conversation identity are retained when known.
User submitted inputApplication submission hook or appropriate existing message event. Record the action without automatically logging prompt bodies or raw keys.
Panel opened / closedAn application/backend hook if available. A screen change alone cannot prove a named action or its cause.
Pause / resume / interruptionRecorder lifecycle with explicit segment and gap semantics.
Text selection / mouse cursorOnly if represented in the capture source or an explicitly supported overlay adapter. Native terminal-client selection may be absent from the watch stream.

Unknown actors, visibility, and timing remain unknown. A hidden-pane event is not hidden-pane footage. Terminal output can itself contain secrets; compression is not redaction. Keep private storage, local assets, and no automatic uploads.

GUI and export: one renderer, bounded reads, no replay from the beginning

Live and historical viewing

Indexed reads select the view at time T and the surrounding activity. Cache immutable content by identity; include theme, layout, font and overlay state in rendered-cache keys. Keep live notifications separate from the user's historical playhead.

Cards display cached thumbnails rather than running one full player each. A card can show “unchanged for 8 hours; recording healthy” without falsely claiming its image is stale. Any extrapolated coverage remains labelled.

Presentation and export

The stock player has no public grid importer. The first adapter candidate projects canonical initial views and bounded row changes as ANSI presentation events into the existing segmented history contract and derived cast video input. It must pass rendered parity tests; it does not reconstruct discarded raw instructions or patch the player.

Use that same visual renderer for GUI and Chromium-based export; FFmpeg produces the video. Pin fonts, glyph widths, palette behavior and animation rules. Compare rendered frames, not only extracted text.

Export recipes can select ranges, alter speed, choose resolution, framing, padding and cursor presentation, and create aligned chapters/metadata. Original geometry is preserved: changing video size must not silently crop, reflow, or make text unreadably small.

Database snapshot discipline

Take a short consistent read to freeze cutoffs and dependencies. Then read immutable records with bounded short transactions. Do not keep a read transaction open throughout a long export; that can pin WAL history and grow disk use.

Actual video size is a separate encoding problem. “One stored view held for eight hours” is compact recording storage, not a promise that an eight-hour MP4 is tiny or free to encode.

Failure isolation, best-effort fidelity, and many-terminal resource use
  • One capture target owns one visual recorder, even when several agents share it. Several targets have independent engines/stores and failure state.
  • Start with the simplest native engine bridge. Benchmark before introducing a shared multiplexing service and its larger failure domain.
  • Batch storage commits within a documented durability budget. Reuse a bounded progress record; do not create a new file per heartbeat.
  • Reserve capture resources. Bound export and thumbnail concurrency, queue sizes, decoded payload sizes, geometry and cache memory.
  • On failure, show the last verified durable endpoint and an explicit gap. Resume requires qualified reinitialization; a visible grid is not a full terminal parser checkpoint.
  • SQLite transactions do not prove semantic integrity. Check payloads, references and ordering. Corrupt or missing data must not be exposed as valid history; salvage only independently validated recoverable content.

Bounded RAM does not imply bounded disk for arbitrary workloads. Genuine output changes and semantic events accumulate. No quota, rolling deletion, or unapproved lifecycle automation is added by this proposal.

Delivery plan, with stop/go evidence

First useful vertical slice

One synthetic terminal → visual database → live view → scrub backward → export a clip while capture continues.

The Go-first UX is already merged. The approved agent-reel-visual-recording epic now begins with baseline/scope reconciliation, followed by timing and visual-format work beneath the existing UI. Qualification and operator approval precede any default-writer switch. Frontloop owns current task status.

1

Establish timing and presentation rules

Build the idle/delayed-input fixture corpus and define visual boundaries, source ordering, clock correlation, and durable cutoffs.

Gate: idle events have defensible placement; delayed input cannot rewrite frozen exports; no hidden temporal thinning. Block precise-coverage claims if capture timing cannot support them.

2

Extend and qualify visible readout

Extend the existing pinned avt helper; prove its visible readout and renderer projection together. Compare interpreted and rendered views for text, styles, Unicode, resize, cursor, alternate screen, and repeated redraws.

Gate: supported visuals agree with the reference path; detected unsupported features produce persistent fidelity annotations while supported recording continues. Early resource measurements at 1/10/32 instances.

3

Build the indexed visual store

Add SQLite-backed reusable rows, complete screen definitions, presentation references, event indexes and durable progress.

Gate: idle replay creates no new visual records; random late seeks are bounded; crash/corruption tests preserve truthful endpoints; WAL growth stabilizes under readers.

4

Connect capture lifecycle and activity

Integrate the visual writer with existing holder ownership. Preserve attribution and privacy, replace lifetime event caps, and retain explicit pause/resume/failure semantics.

Gate: synthetic concurrent recordings and actor events remain correctly separated; events during holds and pauses do not invent footage; short approved diagnostic raw fixtures can validate the new path.

5

Adapt visual inputs beneath the existing GUI

Retain the completed Go application, four adapters and warm Live path; add bounded visual-history readers. Keep the viewing playhead independent of the live recording position.

Gate: browser tests show correct live state, historical event navigation, fidelity warnings, and return-to-live without full-history downloads or capture controls.

6

Export fixed snapshots of ongoing recordings

Freeze source/event cutoffs, apply a non-destructive render/edit recipe, and produce video plus aligned chapter/provenance metadata.

Gate: capture continues during export; rendered-frame comparisons, full video decode and timing assertions pass; repeat exports of the same frozen recipe agree on frames and timing.

7

Qualify endurance, packaging, and controlled rollout

Exercise mixed idle, spinner, dense output, resize and event workloads at 1/10/32 terminals. Use accelerated three-day timelines and a separate real sustained-runtime soak.

Gate: report aggregate CPU/RAM, disk and WAL slopes, commit/seek latency, concurrent export impact and recovery. Actual-backend qualification must pass before normal new captures switch format. Existing archives stay intact; operator activation remains explicit.

8

Optional: compress verified animation loops

Only pursue if measured presentation-timeline growth is significant after content reuse.

Gate: exact observed timing, jitter, resize/divergence boundaries and partial tails survive round-trip and seek tests. Otherwise keep the simpler timed references.

Dependencies, test matrix, and existing Frontloop overlap

Order: timing and engine work establish the format contract; storage enables capture integration; capture/storage enable live GUI; the shared renderer and time map enable export; all feed endurance qualification. Scale probes start early rather than waiting for the final milestone.

Fixtures: unchanged redraws split across source events; typing and scrolling; styled/Unicode cells; cursor and blink; resize; alternate screen; unsupported features; irregular spinner timing; pauses; delayed ingress; queue saturation; disk full; process crashes; corrupt/missing content; old-archive compatibility.

Measurements: per-target and aggregate CPU/RSS, unique-content growth, timed-reference/event growth, commit latency, seek-to-paint, live lag, WAL size, restart/recovery time, and capture behavior while exporting. Proposed performance thresholds must be made explicit against a stated machine/workload; none are measured guarantees today.

Older activity/v1 obligations and change identities remain intact without duplicate implementation or automatic completion. See the baseline document for the full mapping. 06

What to judge before approving

Irreversible trade-off

No guaranteed raw reconstruction

After qualification, the visual format discards redundant instructions. Features the engine cannot represent may be permanently absent—even when capture continues with a warning.

Coverage boundary

This is terminal-view capture

Not desktop video, arbitrary native client overlays, or hidden-pane footage. Supported source content and integration-provided events need an explicit inventory.

Measured, not assumed

Small storage ≠ free capture

The engine still interprets repeated output. Tens of busy terminals, database transactions and export jobs need aggregate benchmarks.

Recommended direction

Proceed toward a visual-state recorder with indexed events and concurrent readers. Make timing and supported-rendering evidence the first gates. Keep your best-effort policy explicit, and defer loop compression until it earns its complexity.

Fable 5.1 advice: what was adopted, and what was not

The advisor was invoked through a Luna wrapper using claude -p --model fable, not a direct Anthropic API agent or Cursor. Response metadata identified claude-fable-5-1; the CLI's authentication status reported claude.ai, first-party provider, and max subscription.

  • Adopt: indexed SQLite/WAL storage per recording, grid-first recording, bounded reads, explicit idle-time clock work, export snapshots, and early many-terminal qualification.
  • Simplify: complete row-reference states instead of long keyframe/delta chains. Native avt is the first bridge candidate; the exact binding is a qualification choice.
  • Do not adopt: independent Go and browser renderers. One shared presentation path reduces visual drift.
  • Do not silently adopt: a debounce window that omits short-lived visual states. Any temporal reduction needs a stated policy and tests.
  • Correct: a heartbeat and receipt-time sample cannot by themselves establish source coverage. Separate source, received, durable, and estimated progress.

The advisor's source review and tests do not qualify the proposed architecture or real capture. Existing documentation has stale constraints/status; the visual-footage direction supersedes raw-byte preservation for the new format, but implementation documentation must be reconciled explicitly.
